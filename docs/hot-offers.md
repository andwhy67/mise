# Горячие предложения

«Что продавать в первую очередь»: блюда, которые помогут продать сырьё с истекающим сроком, — с оценкой 0–100 и объяснением. Формула — PLAN §4.4, код — `src/Mise.Domain/HotOffers`, параметры — секция `HotOffers` в `appsettings.json` (и env `HotOffers__*`).

- `GET /api/v1/hot-offers?limit=5&scorer=v2` — топ с причинами;
- событие `HotOffersChanged` в `/hubs/stock` — при изменении остатков (через общий буфер с дебаунсом) и по таймеру раз в 60 с (время идёт — срочность растёт); отправляется, только если выдача изменилась.

## Формула

Учитываются только **пригодные** партии: Active, с остатком, `expires_at > now`. Просроченные не участвуют.

**1. Давление продукта** *P* (0…1) — насколько продукт «горит»:

| Величина | Формула | Смысл |
|---|---|---|
| Горизонт | `H = min(72 ч, 0,5 × срок)` | срок — норма продукта из словаря; если нормы нет — полный срок партии |
| Риск партии | `hoursLeft < H` | партия вошла в окно риска |
| Срочность партии | `u = (1 − hoursLeft / H)²` | квадрат — резкий рост к концу срока |
| Срочность продукта | `T = max u` | по самой срочной партии |
| Объём | `A = Σ остатка рисковых партий`, `V = min(1, A / baseline)` | `baseline` — среднесуточный расход за 7 дней, без истории — `min_stock_qty`; `baseline = 0` → `V = 1` |
| Давление | `P = T × (0,5 + 0,5 × V)` | большая партия, которая не разойдётся, опаснее маленькой |

**2. Оценка блюда** — только для доступных блюд (`maxPortions ≥ 1`, не выключено вручную):

| Величина | Формула | Смысл |
|---|---|---|
| Доля | `share = q_блюда / Σ q по доступным блюдам с этим продуктом` | ингредиент в нескольких блюдах: вклад делится, больше доля — больше вклад |
| Вклад | `c = P × (0,6 + 0,4 × share)` | |
| Ёмкость | `cap = min(1, maxPortions / 3)` | блюдо на 1–2 порции запас не «сожжёт» |
| Итог | `score = 100 × cap × min(1, max c + 0,25 × (Σ c − max c))` | главный горящий ингредиент + бонус за каждый следующий |

**3. Выдача**: топ-5, сортировка по score, при равенстве — по id блюда (стабильно). **Гистерезис** против мерцания: новое блюдо входит при `score ≥ 15`, уже показанное держится, пока `score ≥ 10`.

**4. Объяснение** (обязательное): `reasons[]` структурно — `productName, atRiskQty, unsoldQty, hoursLeft, expiresAt, qtyPerPortion, portionsBurned, pressure, share, contribution` — и текстом. `headline` — что горит и когда; `explanation` — две главные причины:

> Шпинат: 600 г истекает через 4 ч; в порции 80 г → блюдо поможет списать до 7 порций сырья.

`portionsBurned = min(⌊A / q⌋, maxPortions)` — сколько порций блюда можно сделать из сырья под риском.

## Версии: v1 и v2

Обе реализуют `IHotOfferScorer`, выбираются параметром `scorer` (по умолчанию — `HotOffers:Scorer = v2`), проходят одни и те же сценарии.

- **v1** — дословно §4.4.
- **v2** — v1 + «не успеет разойтись». §4.4 говорит: опаснее партия, которая *не успеет разойтись*. v2 считает это явно: по скорости расхода из истории спрос «съедает» партии в порядке FEFO до истечения каждой; что останется — `unsoldQty`.
  - `V = min(1, unsold / baseline)`, срочность — по партиям, где останется непроданное;
  - давление × `(0,5 + 0,5 × unsold / atRisk)` (`SellThroughFloor = 0,5`): партия, которую спрос разберёт целиком, сохраняет половину давления — оценка скорости неточна, обнулять риск нельзя;
  - без истории расхода v2 совпадает с v1 (это проверяет тест).

## Пример: демо-наполнение (`POST /demo/seed-stock`)

Сразу после наполнения (истории расхода ещё нет, v1 = v2):

| Продукт | Осталось | H | u | A / baseline | P |
|---|---|---|---|---|---|
| Шпинат (норма 72 ч) | 4 ч | 36 ч | (1 − 4/36)² = 0,790 | 600 / 500 → V = 1 | **0,790** |
| Лосось (72 ч) | 12 ч | 36 ч | (1 − 12/36)² = 0,444 | 2000 / 2000 → 1 | **0,444** |
| Сливки (168 ч) | 20 ч | 72 ч | (1 − 20/72)² = 0,522 | 3000 / 2000 → 1 | **0,522** |

Доли: шпинат — лосось на гриле 80 г, паста с курицей 50 г, омлет 40 г (Σ 170); лосось — на гриле 180 г, паста с лососем 100 г (Σ 280); сливки — в шести блюдах (Σ 410 мл).

**«Лосось на гриле со шпинатом»** (7 порций → cap = 1):
- шпинат: c = 0,790 × (0,6 + 0,4 × 80/170) = **0,623**
- лосось: c = 0,444 × (0,6 + 0,4 × 180/280) = **0,381**
- сливки: c = 0,522 × (0,6 + 0,4 × 30/410) = **0,328**
- score = 100 × min(1, 0,623 + 0,25 × (0,381 + 0,328)) = **80,0**

Итоговый топ (тест `DemoScenarioTests`):

| # | Блюдо | Score | Почему |
|---|---|---|---|
| 1 | Лосось на гриле со шпинатом | 80,0 | горят все три: шпинат (4 ч), лосось (12 ч), сливки (20 ч) |
| 2 | Паста с курицей и шпинатом | 65,5 | шпинат + сливки |
| 3 | Омлет со шпинатом и фетой | 54,8 | шпинат — самый срочный, хоть доля и меньше |
| 4 | Паста с лососем в сливочном соусе | 44,6 | лосось и сливки горят мягче |
| 5 | Крем-суп из шампиньонов | 36,4 | только сливки |

Блюда с креветками в рекомендации не попадают (креветок нет — блюда в стопе), блюда без горящих ингредиентов — тоже.

## Проверка качества

- **Юнит-сценарии** (`tests/Mise.Domain.Tests/HotOffers`), обе версии: (а) горящие сливки поднимают блюда со сливками; (б) большая партия весит больше маленькой; (в) недоступное блюдо не рекомендуется и не забирает долю; (г) ингредиент в трёх блюдах — выше блюдо с большей долей; (д) просроченная партия игнорируется; (е) два горящих ингредиента дают бонус; свежая партия за горизонтом не горит; блюдо на одну порцию — ×1/3; score монотонно растёт к концу срока; горизонт — от нормы продукта, без неё — от срока партии; v2: партия, которую спрос разберёт, — ниже; без истории v2 = v1; гистерезис; текст объяснения.
- **Прогон на симуляторе** (Docker): сразу после демо-наполнения — топ как в таблице выше; после «часа» нормальной работы (симулятор разобрал и довёз продукты) рекомендаций нет — ничего не горит; в сценарии Spoilage топ заполняется блюдами из сырья со сроком 20–30 мин (score 79–100), объяснения называют конкретные продукты и минуты.
- **Найдено итерацией и исправлено**: (1) идея считать горизонт от срока конкретной партии (а не нормы продукта) давала обратный эффект — партия со сроком 10 ч за 4 ч до конца казалась неопасной; отказались, горизонт — по §4.4. (2) в v2 блюдо держалось в топе со score ≈ 20 из-за 80 г лосося, которые, по самому же объяснению, «спрос успеет разобрать»: добавлен множитель `SellThroughFloor` — такие позиции опускаются ниже порога.

## Параметры (`HotOffers`)

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `Scorer` | `v2` | версия по умолчанию (`v1`, `v2`) |
| `MaxHorizonHours`, `HorizonShelfFraction` | 72, 0,5 | горизонт риска |
| `VolumeBaseWeight` | 0,5 | доля давления, не зависящая от объёма |
| `ShareBaseWeight` | 0,6 | доля вклада, не зависящая от доли блюда |
| `SecondaryBonus` | 0,25 | бонус за каждый следующий горящий ингредиент |
| `SellThroughFloor` | 0,5 | v2: остаток давления, если партия разойдётся сама |
| `FullCapacityPortions` | 3 | порций для полной ёмкости |
| `EnterThreshold`, `ExitThreshold` | 15, 10 | гистерезис |
| `TopN` | 5 | размер выдачи |
| `HistoryDays` | 7 | окно истории расхода |
| `RefreshSeconds` | 60 | пересчёт по таймеру |

## Допущения

- Расход по истории — чистое списание под заказы (минус возвраты при отмене) за 7 дней; делитель — длительность истории, но не меньше суток (несколько минут работы не превращаются в огромную скорость).
- Скорость в v2 — плоская (без профиля «час дня»); EWMA с профилем — фаза 6 (прогноз).
- Гистерезис хранится в памяти инстанса API; при нескольких инстансах у границы порога выдачи могут кратко расходиться.
- `HotOffersChanged` несёт топ целиком (он маленький, клиенту нужен порядок), а не дельту.
