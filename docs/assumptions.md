# Допущения

Принятые решения по неоднозначным местам кейса и плана. Источник вопросов — PLAN.md §14; пока эксперт не ответил, работаем по ним.

## Из PLAN.md §14 (приняты все по умолчанию)
1. Срок годности: явная дата → `createdAt` поставки + срок позиции → `default_shelf_life` из словаря → иначе 400.
2. Просроченное полностью исключается из доступного остатка (`usable`) и из заказов.
3. Единицы: ввод может быть в кг/л, хранение — в г/мл/шт (`decimal`).
4. Состав блюд — словарь в нашей системе, редактирует менеджер.
5. Заказы создают Chef/Manager в UI и Simulator как внешний источник; роли «официант» нет.
6. Отмена заказа возвращает продукты в те же партии, если они ещё не просрочены.
7. Стоп-лист: и по нехватке ингредиентов, и ручное отключение блюда.
8. Нагрузка: до ~10 заказов/с, ~25 продуктов, ~18 блюд.
9. Вместо apk — PWA, устанавливаемая на телефон.
10. Сдача: README + docs/demo.md + (опц.) видео.
11. Время хранится в UTC, отображается в Europe/Moscow, 24-часовой формат.
12. Интеграции (iiko/1С/Честный знак) только эмулируются; расширяемость через `ISupplySource`.

## Уточнения, найденные при разборе плана (фаза 0)
| # | Вопрос | Решение |
|---|---|---|
| A1 | PLAN §1 пишет `delivered_at + shelf_life`, §3.2 — `received_at = supplies.created_at` | Источник истины — §3.2; термин `delivered_at` не используем |
| A2 | Явный `expiresAt` ≤ `createdAt` поставки | 400 (некорректная позиция). Партия, истёкшая к моменту приёма из-за `createdAt` в прошлом, принимается сразу в статусе `Expired` |
| A3 | `createdAt` присылает клиент | Не прислан → `IClock.UtcNow`; в будущем больше чем на 5 мин → 400 |
| A4 | Тот же `number` поставки с другим `Idempotency-Key` | 409 Conflict |
| A5 | Hot offers: `baseline_p = 0` (нет истории и `min_stock_qty = 0`) | `V_p = 1` (объём считается максимальным) |
| A6 | Пороги статуса срока «≤ 50 % / 24 ч», «≤ 20 % / 6 ч» | Статус наступает, когда выполнены **оба** условия (доля И часы). Так у долгих продуктов (30 дн.) Warning — за 24 ч, а не за 15 дней, а у коротких (12 ч) — на половине срока, а не сразу при приёмке. Пороги — `Stock:ShelfLife` в конфиге. *Пересмотрено в фазе 1: изначально было OR.* |
| A7 | Redis-кэш доступности и транзакция заказа | Заказ проверяется только по БД под `FOR UPDATE`; кэш — для чтения/UI |

## Фаза 1: справочники, поставки, партии
| # | Вопрос | Решение |
|---|---|---|
| B1 | Неизвестный `productId` в позиции поставки | 400 с ошибкой на поле позиции. Справочник ведёт менеджер, автосоздания продуктов из поставки нет |
| B2 | `Idempotency-Key` | Необязателен. Если передан: тот же ключ + то же тело → 200 и прежняя поставка; тот же ключ + другое тело → 409 `supply.idempotency_key_reused`. Без ключа дубли ловят уникальные `number` и `id` (409) |
| B3 | Удаление/изменение продукта, который уже используется | Удаление → 409 `product.in_use`; смена единицы измерения → 409 `product.unit_locked` (количества в партиях и составах записаны в старой единице). Мягкая деактивация — позже при необходимости |
| B4 | Название продукта в позиции поставки | Хранится как snapshot (`supply_items.product_name`); если не передано — берётся из словаря |
| B5 | Ввод в кг/л | В позиции поставки можно указать `unit` (`Kilogram`, `Liter`, …): пересчитывается в базовую единицу продукта; несовместимые единицы → 400. Точность — до 0,001 базовой единицы |
| B6 | Статус продукта в `/stock` | Худший статус срока среди пригодных партий; `OutOfStock`, если пригодных нет (просроченный, но не списанный остаток показывается отдельно — `expiredQty`) |
| B7 | Приём поставки «задним числом» | `createdAt` в прошлом допустим. Позиции, срок которых уже истёк к моменту регистрации, принимаются в статусе `Expired` (в остаток не входят) |
| B8 | Авторизация на эндпоинтах | Пока не включена — роли и JWT в фазе 7 |
| B9 | Порядок партий с одинаковым сроком | FEFO: `expires_at`, затем `id` (Guid v7 — по времени регистрации) |

## Фаза 2: заказы, FEFO, стоп-лист
| # | Вопрос | Решение |
|---|---|---|
| C1 | Отказ при нехватке | 422 `order.insufficient_stock` с `missing[]`: продукт, единица, `required`, `available`, `shortage` и блюда заказа, которым он нужен. Транзакция откатывается — ничего не списывается |
| C2 | Заказ с вручную выключенным блюдом | 422 `order.dish_unavailable` со списком блюд |
| C3 | Отмена заказа | Только из `Created`/`Cooking`; `Done` и повторная отмена → 409. Возврат — в те же партии, если они ещё не просрочены и не списаны; иначе объём попадает в `lost[]` ответа (потеря) |
| C4 | Смена статуса | Только вперёд: `Created → Cooking → Done` (или сразу `Done`); назад → 422 `order.invalid_transition`; повтор текущего статуса — no-op |
| C5 | Номер заказа | `ORD-000001…` из последовательности PostgreSQL (пропуски номеров после отказов допустимы) |
| C6 | Redis-кэш доступности | Пока не используется: пересчёт на ~26 продуктах дешёвый, а проверка заказа всё равно идёт по БД под `FOR UPDATE` (A7). Кэш/дельты — в фазе 4 вместе с SignalR, если понадобится |
| C7 | Стоп-лист | Считается вживую при каждом `GET`. История (`stoplist_history`) фиксирует переходы при пересчёте после поставки, заказа, отмены и изменения блюда; переход «партия истекла сама по себе» фиксирует тик `ExpiryWorker` (фаза 3, D5) |
| C8 | Причина стопа | `Manual` приоритетнее `Shortage`: выключенное вручную блюдо показывается как Manual, даже если ингредиентов тоже нет |
| C9 | Удаление блюда с заказами | 409 `dish.in_use` — предлагается выключить блюдо (`isActive=false`) |

## Фаза 3: сроки, алерты, автосписание
| # | Вопрос | Решение |
|---|---|---|
| D1 | Когда поднимать «скоро истечёт» | Тик сравнивает текущий уровень партии (правило A6, AND) с уже поднятыми: один алерт на партию и уровень (ключ `batch:{id}:{level}`). Если тик «проскочил» Warning — сразу Critical, Warning задним числом не создаётся |
| D2 | Важность алертов | ExpiringSoon — Warning/Critical по уровню; Expired — Critical, если остаток лежит на складе, Warning, если уже списан автоматически; LowStock — Warning, Critical при нулевом остатке; StopListOn — Warning, StopListOff — Info |
| D3 | «Состояния» и «события» | ExpiringSoon и LowStock закрываются сами (`resolvedAt`), когда причина ушла (партия израсходована/списана/истекла; остаток восстановлен). Expired и StopListOn/Off — события, не закрываются, только подтверждаются (`ack`, идемпотентно). `GET /alerts/summary` считает неподтверждённые и актуальные |
| D4 | Автосписание | По умолчанию включено (`Expiry__AutoWriteOff`): весь остаток партии → движение `ExpiryWriteOff` («Истёк срок годности»), статус `WrittenOff`. Выключено — партия только переходит в `Expired`, алерт Critical, списание вручную. Партии, принятые уже просроченными, тоже закрываются тиком |
| D5 | Стоп-лист после просрочки | После каждого тика — пересчёт стоп-листа (даже если ничего не списано: партия могла просто истечь) → интервал в `stoplist_history` с ограничивающим продуктом и алерт StopListOn |
| D6 | LowStock | Только для продуктов с `minStockQty > 0`, по usable (без просроченного). Один открытый алерт на продукт; проверяется на тике (задержка до `IntervalSeconds`) |
| D7 | Несколько инстансов | Тик в транзакции под `pg_try_advisory_xact_lock('expiry-worker')`: занят — тик пропускается. Партии к закрытию блокируются `FOR UPDATE` в порядке заказов (`product_id, expires_at, id`) — без дедлоков с ними. За тик — не больше `BatchSize` (500) партий |
| D8 | Ручное списание | `POST /batches/{id}/write-off`: причина обязательна (≤ 500 символов), количество необязательно (по умолчанию весь остаток, можно в `unit` — кг/л). Активную или просроченную партию; израсходованную/списанную — 409 `batch.not_writable`, больше остатка — 422 `batch.insufficient_quantity`. Без Idempotency-Key: повтор полного списания получит 409 и не спишет дважды |
| D9 | Не входит в фазу | Пуш алертов в SignalR — фаза real-time (сервисы возвращают изменения); «перемотка времени» для демо — позже, в окружении Demo (PLAN §15); роль пользователя в движении — с появлением авторизации |

## Фаза 4: real-time и симулятор
| # | Вопрос | Решение |
|---|---|---|
| E1 | Что и когда пушить | Сервисы после коммита сообщают «что изменилось» (продукты, партии, блюда, стоп-лист, алерты, заказы, поставки); за окно дебаунса (`Realtime__DebounceMilliseconds`, 250 мс) изменения склеиваются, полезная нагрузка читается из БД в момент отправки — клиент получает последнее состояние, а не промежуточные |
| E2 | Состав событий | PLAN §7 + `AvailabilityChanged` (maxPortions блюд с затронутыми продуктами) и `OrderStatusChanged`. `StockChanged` несёт полную строку остатка (как `GET /stock`), `StopListChanged` — вошедшие блюда с причиной и ограничивающим продуктом. Блюдо, вошедшее и вышедшее в одном окне, придёт только как «вышло». `HotOffersChanged` — фаза 5 |
| E3 | Надёжность доставки | Best effort: ошибка отправки логируется, запрос не падает. Источник истины — REST: клиент после реконнекта делает refetch. Redis backplane (`mise:signalr`) доставляет события клиентам всех инстансов API |
| E4 | Симулятор и API | Симулятор — отдельный процесс и внешний клиент REST (как касса/склад). Управление — через Redis: API пишет желаемое состояние (`version` растёт), симулятор применяет его по версии и раз в секунду пишет heartbeat (ключ с TTL 15 с → `online`) |
| E5 | Скорость ×1…×60 | Ускоряет модельное время симулятора (поток заказов по суточной кривой, интервал поставок), но не часы API: сроки годности идут по реальному времени. Быстрое «старение» в демо даёт сценарий Spoilage (сроки 5–30 мин); перемотка часов API — отдельная фича Demo (PLAN §11) |
| E6 | Модель ресторана | Заказы — пуассоновский поток по суточной кривой (Москва: пики обеда и ужина), 1–4 блюда, веса по категориям; закрываются через 15 модельных минут; 1% заказов отменяется (Chaos — 15% + всплески и повторы с тем же Idempotency-Key). Поставки — по точке заказа (1,5 × минимум) до цели (3 × минимум), кратно упаковке, не больше 100 позиций. Смена сценария — немедленная проверка запаса |
| E7 | Ретраи симулятора | Стандартный resilience-хендлер: сетевые ошибки, 5xx, 408, 429 с экспоненциальной паузой; POST безопасны благодаря Idempotency-Key. 422 — нормальный исход («не хватает»), считается в статистике, не ретраится |
| E8 | Демо-наполнение | `POST /demo/seed-stock` (флаг `Demo__Enabled`): три поставки через обычный приём — свежий запас; лосось, сливки (Warning) и шпинат (Critical) «двухсуточной давности»; бекон на 2 карбонары; креветок нет. Номера `DEMO-yyyyMMdd-NN` = Idempotency-Key: повтор в тот же день — 200 без дублей |
| E9 | Пока без авторизации | Хаб и управление симулятором открыты; JWT и роль `Simulator` — фаза 7 (в HTTP-клиенте симулятора есть место под токен) |
| E10 | Общий протокол | Контракты Redis-протокола (`SimulatorProtocol.cs`) лежат в Application и подключаются в симулятор ссылкой на файл — без зависимости симулятора от слоёв API |

## Фаза 5: горячие предложения (подробно — docs/hot-offers.md)
| # | Вопрос | Решение |
|---|---|---|
| F1 | Какая формула | §4.4 дословно — `v1`; по умолчанию `v2` = v1 + «не успеет разойтись» (объём и давление по тому, что обычный спрос не разберёт до истечения). Версия — `HotOffers__Scorer` или `?scorer=` |
| F2 | `shelf_life_p` в горизонте | Норма продукта из словаря; если нормы нет — полный срок партии (`expires_at − received_at`) |
| F3 | `baseline_p` | Среднесуточный чистый расход под заказы за 7 дней (делитель ≥ 1 суток); без истории — `min_stock_qty`; 0 → `V = 1` (A5) |
| F4 | Какие блюда рекомендуются | Только доступные: `maxPortions ≥ 1` и не выключенные вручную; доля продукта считается среди них |
| F5 | Порог и мерцание | Топ-5; вход при score ≥ 15, выход при < 10 (гистерезис в памяти инстанса); при равенстве — по id |
| F6 | Когда пересчитывать | При любом изменении остатков/партий/блюд/стоп-листа (общий буфер, 250 мс) и по таймеру раз в 60 с; событие — только если изменились состав, порядок или score на 1+ |

## Фаза 6: расход, прогноз, поставки, аналитика (подробно — docs/forecast.md)
| # | Вопрос | Решение |
|---|---|---|
| G1 | Что считать расходом | Чистое списание под заказы: `OrderConsumption` минус `OrderCancelReturn`. Списания по сроку и вручную — не спрос, в расход не входят |
| G2 | Как вести consumption_hourly | Не в транзакции заказа (не нагружаем горячий путь), а идемпотентным пересчётом из журнала: фоновый воркер раз в минуту + перед прогнозом/отчётом |
| G3 | Скорость | EWMA по часам (α 0,08), пустые часы — нули; профиль «час дня» при ≥ 3 днях истории; уверенность Low/Medium/High по длине истории. Hot offers v2 используют ту же оценку |
| G4 | Прогноз стоп-листа | Симуляция с шагом 15 мин: спрос по FEFO + истечение партий; ETA — когда остатка ингредиента меньше порции. Только для доступных блюд |
| G5 | Формула поставок | §4.6 + `cap ≥ min_stock_qty`, без истории — довоз до минимума (иначе предложение было бы пустым). Черновик поставки (COULD) не делаем |
| G6 | Списания в деньгах | Нет закупочных цен — только количество и число операций (§4.7 [COULD]) |
| G7 | Доля списаний в KPI | Единицы у продуктов разные — доля считается по каждому продукту (списано / поступило за период), итог — среднее по продуктам с поставками |
| G8 | «Сегодня» | Сутки по Москве (фиксированное UTC+3, без tzdata) |
| G9 | Время ниже минимума | По интервалам алертов LowStock (открыт → закрыт), а не по непрерывному ряду остатков |
| G10 | Grafana | `grafana/grafana:13.2.3`, порт 3001, provisioning источника и 2 дашбордов; анонимный просмотр включён для демо (`GRAFANA_ANONYMOUS`). Подключение к БД — под основной учёткой; роль только на чтение — фаза 7 |

## Технические
| # | Вопрос | Решение |
|---|---|---|
| T1 | .NET 10 SDK на машине разработки отсутствует (есть 9.0.318) | Используем `net9.0` (fallback из CLAUDE.md). Переход на 10 — смена TFM в `Directory.Build.props`, `global.json` и базовых образов |
| T2 | TypeScript 7 не поддерживается `typescript-eslint` (peer `<6.1`) | Фиксируем `typescript@6.0.3` |
| T3 | Порты по умолчанию | API `5080` (хост; внутри контейнера 8080), web (nginx) `8081`, Vite dev `5173`, Postgres `5432`, Redis `6380` (хост; внутри сети 6379). БД и Redis публикуются только на 127.0.0.1. Всё переопределяется через `.env` |
| T4 | В compose фронт и API на одном origin | nginx проксирует `/api`, `/health`, `/swagger`, `/hubs` на API — CORS нужен только для dev-сервера Vite |
| T5 | Миграции | Применяются при старте API, если `Database__MigrateOnStartup=true` (в compose — включено) |
| T6 | Уязвимость SignalR (CVE-2026-70159, DoS) | Пакеты SignalR — 9.0.21 (исправленная версия); в образе API рантайм ASP.NET 9.0.21. Локально для dev-запуска стоит обновить .NET Runtime 9 до 9.0.21+ |
