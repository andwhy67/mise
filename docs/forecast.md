# Расход, прогноз стоп-листа, предложения поставок

Код — `src/Mise.Domain/Forecasting` (чистые функции, юнит-тесты), сервисы — `src/Mise.Application/Forecasting`, параметры — секция `Forecast` в `appsettings.json` (env `Forecast__*`).

## 1. Расход: `consumption_hourly`

Агрегат по часам из неизменяемого журнала движений: `qty = −Σ qty_delta` для `OrderConsumption` (списание под заказ) и `OrderCancelReturn` (возврат при отмене) — то есть **чистый** расход.

Пересчёт — один SQL (`INSERT … SELECT date_trunc('hour', created_at, 'UTC') … ON CONFLICT DO UPDATE`): часы начиная с последнего записанного минус час (запас на транзакции, закоммиченные позже своего `created_at`). Идемпотентен, при нескольких инстансах сериализуется advisory lock-ом. Запускается фоновым воркером раз в минуту и перед каждым прогнозом/отчётом — данные всегда свежие.

## 2. Скорость расхода (EWMA)

- История — 7 дней (`HistoryDays`), начиная с первого списания под заказ (по всем продуктам): продукт, который не заказывали, честно имеет скорость 0. Пустые часы — нули, а не «нет данных».
- **Плоская скорость** — EWMA по часам, `α = 0,08` (≈ 2 / (24 + 1): память порядка суток). Начальное значение — среднее первых 24 ч (меньше смещение). Если полных часов ещё нет — расход текущего часа / прошедшее время (не меньше 15 мин).
- **Профиль «час дня»** — при ≥ 3 днях истории: для каждого часа суток EWMA по дням (`α = 0,5`). Ожидаемый расход на интервале — интеграл профиля по часам.
- **Уверенность**: `Low` — меньше суток истории или расхода не было; `Medium` — меньше 3 дней; `High` — 3 дня и больше (есть профиль).

## 3. Прогноз остатка

Пошаговая симуляция (шаг 15 мин + точные моменты истечения партий): ожидаемый спрос списывает пригодные партии **по FEFO**, на `expires_at` несъеденный остаток партии пропадает. Результат — кривая остатка, сколько уйдёт в заказы, сколько истечёт, когда спрос перестанет покрываться.

## 4. Прогноз стоп-листа — `GET /stoplist/forecast?horizonHours=24`

Для каждого **доступного** блюда — первый момент, когда прогнозный остаток любого ингредиента станет меньше порции:

| Поле | Смысл |
|---|---|
| `eta`, `hoursLeft` | когда блюдо уйдёт в стоп |
| `limitingProduct` | ингредиент, на котором это случится (остаток, скорость) |
| `cause` | `Consumption` — съедят заказы; `Expiry` — партия истечёт, а остального не хватит на порцию |
| `confidence` | по истории расхода ограничивающего продукта |
| `explanation` | «"Сыр фета" расходуется ≈147 г/ч: остатка 210 г хватит на 57 мин, потом меньше порции (70 г).» |

Без истории расхода прогноз всё равно ловит стоп из-за истечения партий (`confidence = Low`).

## 5. Предложения поставок — `GET /supply-suggestions?horizonHours=72`

PLAN §4.6 на горизонте `Hz` (по умолчанию 72 ч):

```
demand    = ожидаемый расход за Hz (профиль/плоская скорость)
projected = текущий остаток − то, что истечёт неиспользованным за Hz   (из симуляции)
safety    = max(min_stock_qty, скорость × 12 ч)
need      = max(0, demand + safety − projected)
cap       = max(скорость × срок годности, min_stock_qty)               // не больше, чем успеем использовать
suggest   = ⌈min(need, cap) / pack_size⌉ × pack_size
```

Отличия от формулы плана (обе — чтобы рекомендации не обнулялись без истории):
- `cap` не ниже `min_stock_qty`: без истории `скорость × срок = 0`, и предложение всегда было бы пустым;
- без истории `demand = 0`, `safety = min_stock_qty` — система предлагает довезти до минимального остатка (и пишет об этом в причинах).

**Срочность**: `Critical` — кончится в течение 12 ч или пригодного остатка нет; `High` — в течение суток или уже ниже минимума; иначе `Normal`.

**Причины** (текстом): «исчерпается через 14 ч», «ниже минимального остатка (400 г при минимуме 500 г)», «1,2 кг истечёт неиспользованным», «объём ограничен сроком годности: больше не успеем использовать до порчи», «нет истории расхода — довозим до минимального остатка».

## 6. Важно для демо

Скорость симулятора (×1…×60) ускоряет поток заказов, но не часы API (docs/assumptions.md, E5). На ×60 за реальную минуту приходит шестьдесят модельных минут заказов, и скорость расхода в реальном времени тоже в 60 раз выше ресторанной — прогнозы и объёмы поставок честно это отражают («заказать 24 кг»). Для правдоподобных чисел прогноза — гонять симулятор на ×1–×5.

## Параметры (`Forecast`)

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `HistoryDays` | 7 | окно истории |
| `FlatAlpha`, `ProfileAlpha` | 0,08, 0,5 | сглаживание EWMA |
| `ProfileMinDays` | 3 | с какого объёма истории включается профиль «час дня» |
| `StepMinutes` | 15 | шаг симуляции |
| `StopListHorizonHours` / `MaxStopListHorizonHours` | 24 / 72 | горизонт прогноза стоп-листа |
| `SupplyHorizonHours` / `MaxSupplyHorizonHours` | 72 / 336 | горизонт планирования поставок |
| `SafetyHours` | 12 | страховой запас в часах расхода |
| `AggregationIntervalSeconds` | 60 | фоновый пересчёт consumption_hourly |
